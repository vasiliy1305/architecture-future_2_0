## Пояснение к целевой архитектуре

Целевая архитектура строится как событийная data-platform с доменными сервисами и self-service аналитикой. Переход выполняется поэтапно, поэтому в течение миграции сохраняются мосты совместимости с legacy DWH и ESB.

### Как мигрирует ESB (Apache Camel)

Существующая ESB не заменяется одномоментно на брокер сообщений, так как в ней уже сосредоточены:
- маршрутизация интеграций;
- трансформации форматов;
- ФЛК и валидация сообщений;
- синхронные интеграции со старыми системами;
- оркестрация части бизнес-процессов.

Поэтому в целевой архитектуре её функции раскладываются на несколько компонентов:

1. **Event Bus**  
   используется только для асинхронной доставки событий между доменами; сам по себе не заменяет ESB-логику.

2. **Data Integration Layer**  
   берёт на себя ETL/ELT-потоки, API-интеграции, CDC, трансформации данных, валидацию, анти-коррупционный слой и адаптеры к legacy-системам.

3. **ACL / Compatibility adapters**  
   обеспечивают совместимость со старыми контрактами Camel и DWH на этапе миграции.

Стратегия миграции ESB:
- на первом этапе Camel остаётся мостом совместимости;
- новые интеграции строятся через события и API;
- существующие потоки постепенно выносятся из Camel в доменные сервисы и слой интеграции;
- после выноса критичных маршрутов и трансформаций Camel выводится из критического пути и затем выводится из эксплуатации.

### Как мигрирует DWH

Legacy DWH на SQL Server 2008 не развивается как точка концентрации бизнес-логики. Его роль постепенно сужается до источника исторических данных и временного поставщика отчётности.

Стратегия миграции DWH:
- сначала DWH остаётся источником для части BI-отчётности;
- данные из legacy DWH и операционных систем реплицируются в новую аналитическую платформу;
- новая бизнес-логика и новые витрины больше не реализуются в legacy DWH;
- доменные данные публикуются через события, CDC и API;
- self-service портал и новые витрины работают уже поверх новой платформы данных;
- после переноса ключевых витрин legacy DWH переводится в режим только для чтения и архивного хранения, а затем выводится из эксплуатации.

### Lakehouse Platform - это не legacy DWH и не гибрид старого хранилища

На диаграмме под `Lakehouse Platform` имеется в виду **новая целевая аналитическая платформа класса Lakehouse**, а не старый SQL Server DWH.

То есть:
- **Legacy DWH** = старое корпоративное хранилище на SQL Server 2008;
- **Lakehouse Platform** = целевая платформа для аналитики, self-service BI, batch и near-real-time сценариев.

Почему выбран такой подход:
- нужны независимые доменные витрины;
- нужны batch + near-real-time сценарии;
- нужно подключать новые источники без встраивания логики в старый DWH;
- важно отделить аналитическую платформу от legacy-монолита.

### Что имеется в виду под ETL / ELT / CDC / APIs / ACL

Под `ETL / ELT / CDC / APIs / ACL` в контейнере `Data Integration Layer` понимаются четыре типа интеграции:

1. **ETL/ELT**  
   пакетная загрузка данных из legacy DWH, внешних систем и внутренних БД в аналитическую платформу.

2. **CDC**  
   инкрементальная доставка изменений из транзакционных систем и legacy-хранилища.

3. **API integrations**  
   синхронные интеграции с внешними и внутренними сервисами там, где событийная модель пока невозможна.

4. **Validation / transformation / mapping**  
   ФЛК, нормализация, преобразование форматов, маппинг legacy-контрактов в доменные контракты.

Иными словами, `Data Integration Layer` - это не просто “загрузка данных”, а отдельный слой миграционной и интеграционной логики между legacy-ландшафтом и новой платформой.
